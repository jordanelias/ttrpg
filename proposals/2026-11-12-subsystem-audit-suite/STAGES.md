How the two orders are reconciled: **dependencies fix the sequence of batches; the requirements fix the grouping and the milestones.** Concretely: (1) v12 carries a **requirement map**: each batch names the requirement rows it advances and the row state it is expected to move to (not_met to partial to met), so a reader sees which batches meet which requirement; (2) where dependencies allow a choice, batches that complete a requirement are scheduled before batches that only prepare ground for later ones, and the batches that every requirement stands on (the owners, the one resolver and dice rulings, the keyed draw, the capability architecture) come first by dependency, not by preference; (3) each batch's gate includes the execution artifact that moves its requirement row (the register's `--requirements` reading and `tools/m1_acceptance.py --summary` rows that execute), so no batch claims a requirement by writing; (4) the requirement count the register reports at each batch boundary is recorded in the batch's close, as a reading and never as a count in a pointer index (CLAUDE.md §1); (5) a batch that serves no requirement and no ruling of Jordan's is named, with its reason, or cut. The master suite and v12 are authored by the ordinary lanes (Fable authors, Sonnet reviews); no stage before v12's adoption invokes `methodology-execute`. v12's head states that its batches are executed by `/methodology-execute` and gives the invocation per batch (`/methodology-execute Batch <handle>`), and its batch structure is written so that the skill can follow it as stated.
   - **v12 is written to be run by `methodology-execute`** (Jordan, 2026-11-12: *"must be sequenced in careful logic batches based on interdependencies, but also must be efficient. should using methodology-execute"*). The skill follows a plan's own batch structure as stated and derives nothing the plan states, so v12 states it in the forms the skill recognises (`.claude/skills/methodology-execute/SKILL.md`, §BATCHES):
     1. **A batch table with handles**, positions in dependency order, and a `Batch` column on the position table; an explicit boundary row `STOP. Batch N closes here` after each batch; gates that name batches (`GATE: Batch N`, met when that batch's close has landed).
     2. **Each position is a content-owner entry** with INSTRUCTION, WHERE (the files it edits), FALSIFIER and GATE, and the plan's own **serial-edge table and file-census table**, so the partition (items are linked when their edit sets intersect, their gate sets intersect, or one gates on the other) can be read, not guessed.
     3. **Logic**: batches are the connected groups of linked items, ordered so every gate points from an earlier item to a later one. A group is cut only along links that point forward, and the cut is stated with what carrying the whole group would have risked. No batch gates on a later batch. **A batch has ONE close** (RULED, 2026-11-06); a card with several closes is written as several batches.
     4. **Efficiency**: unlinked groups are kept apart or merged by a stated reason (apart buys a cleared window at the cost of a full close; merged saves a close at the cost of the union of their contexts); every deliberate hash mover in a batch is declared and co-batched so a seeded re-pin happens once per batch, not once per item; batches with disjoint edit sets are marked as able to run in parallel (producers in `isolation: worktree`); items that are cheap and safe are grouped so the expensive close (the review fan, the one suite run, the terminal critique) is paid per batch, never per item; the cost class and model tier (CLAUDE.md §10) is stated per item.
     5. **A context set `C(k)` per batch** (its reading list), so a cleared window can reopen the batch from disk; nothing is carried by recollection. The batch's finished positions are deleted from the plan at its expunge (the commit is the record).
     6. The in-flight row lives in the Open table of the lane's `registers/handoffs/HANDOFF_<LANE>.md`; v12 names the lane for each batch.

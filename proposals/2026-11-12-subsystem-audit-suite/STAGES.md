## Parallel sessions in v12 (Jordan, 2026-11-12: *"can we set up plan so that it can run parallel sessions"*)

Yes, with rules; v12 is structured for it. What the repository already gives: batches in different lanes have separate in-flight rows (`registers/handoffs/HANDOFF_<LANE>.md`), the ED ledger is lane-split, parallel write lanes use `isolation: worktree` (CLAUDE.md §10), and `create_session` and `send_message` are deliberately not denied (CLAUDE.md §11). What forbids it: `methodology-execute` allows ONE open batch per lane's in-flight row and `STOPPED`s an invocation that does not match it, so **parallelism is across lanes, never inside one**. v12 therefore carries:

1. **A lane tag on every batch** (the nine-lane roster of `tools/ci_common.py`: MB, PC, FI, SC, FA, WR, IN, GO, SE), and at most one open batch per lane at a time.
2. **Waves.** v12 groups batches into waves: a wave is a set of batches that may run at once because (a) their edit sets are disjoint (the file-census table), (b) no gate runs between them, (c) they are in different lanes, (d) their hash-mover sets do not collide (below), and (e) a concurrency cap is stated (the machine's cores and the cost class). The wave order is the dependency order; the critical path is named.
3. **Hash movers in parallel.** Two batches that both move seeded goldens cannot both re-pin independently. v12 either serialises them (the later batch re-reads the earlier's after-reading as its baseline, `reading @<sha>`) or marks which batches are hash-EQUAL (any number may run in parallel) and puts movers in a declared merge order; the later mover rebases and re-pins once.
4. **Ids allocated up front.** A prelude batch (IN lane) allocates every id v12 will need (`references/id_reservations.yaml` `next_free`, lane-tagged `ED-<LANE>-NNNN`) in per-batch blocks and lands the bump on `main` before any session cites a number (CLAUDE.md §4: renumbering does not escape a collision).
5. **Permanent-surface collisions.** The registers every position appends to (the hole register, the requirements register, `CURRENT.md` rows) are single files: v12 names, per batch, the rows it appends, assigns each parallel batch distinct row ids in advance (a block), and gives the merge order; conflicts in append-only files are resolved by keeping both rows, never by regenerating.
6. **One branch and worktree per session, one PR per batch**, based on the wave's base commit; the merge queue is the dependency order; a session never edits another lane's files or opens another lane's batch; a conflict with a sibling is a STOP reported to the coordinator, not a silent rebase onto someone else's work.
7. **A coordinator.** One session (this orchestrator role) opens a wave with `create_session` per batch (prompt: `/methodology-execute Batch <handle>`, lane, worktree, base SHA, id block, row block, merge position), reads their `STOPPED` and status lines, merges in order, re-bases the next wave, and does not poll an external service (CLAUDE.md §11); sessions are watched through our own agents and local processes only.
8. **Checks.** Each session runs its own BATCH-CLOSE and the covering tests; the full suite and CI run once per merged wave on the integrated head (CLAUDE.md §0.4: at most once per commit and only where it can observe something), so parallelism does not multiply the expensive close.

**The standalone-playable test (subsystem lanes).** A subsystem is a standalone playable game when, with the other subsystems stubbed at their declared interface, a player (or the chooser standing in for one) can enter it, make choices that matter, reach an ending (win, lose or draw; never a dead end: A-81, no scene is still), and the world moves because of it (A-80: entrenchment still moves the world); and the same subsystem plugs into the season loop through its registered seam (Layer 1 `04` §A.2, composition rows) with no change. For each subsystem the instruction set states: the entry (the command or harness call), the scripted scenario or generator seed that exercises it, the player-facing surface it needs (from the GO proposals), the stub contract for its neighbours, the stop conditions (ending kinds), the execution artifact that proves each (a named test or a run with its expected reading), and the integrated check (the same subsystem in the loop).

**The item form (each instruction).** `Item: <handle>` · Requirement/subsystem advanced · INSTRUCTION (ordered edits: exact files and symbols at the single owner, schema, call sites) · WHERE (the edit set) · FALSIFIER and control · GATE (an execution artifact and its expected reading; never a document) · hash movers declared · depends on (batch handles and item handles; EXISTS-IN-TREE / PROPOSED / MISSING) · lane tag (MB PC FI SC FA WR IN GO SE) · batch it joins (an existing U3 handle, or a new one with its dependencies) · cost class and model tier (CLAUDE.md §10) · what lands it. An item that merely points at an existing proposal says so and adds only what is missing. An item whose missing part is not decidable from the repository is written with the blocking reason and its owner (never silently dropped).

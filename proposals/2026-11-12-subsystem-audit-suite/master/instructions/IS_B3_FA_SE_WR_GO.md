## 0. What this file is, and how to read an item

**What it is.** For each of four subsystems (faction and governance FA, settlements SE, the world WR, the player surface and port GO): the standalone-playable test of the work order, read against the tree at this SHA and against the suite's proposals; the batch sequence of `unified/U3_DEPENDENCY_ORDER.md` that gets the subsystem to that test; and one `Item:` for each thing the existing proposals do not carry. It does not restate a proposal's edits. An item that points at a proposal says so and adds only what is missing.

**What it is not.** It is not v12 and it moves no requirement row. Every reading quoted as "today" was taken by a command named beside it, at this SHA, on the tree as checked out (implementation lane A's two commits are not in it, `README.md` §6). No proposal is landed, so every "after B-nn" statement is a statement about a document's gate, not about behaviour (CLAUDE.md §0.2). Hashes quoted are examples at this SHA, never targets: B01 re-records every realm pin and B05, B06 move every seeded result once each.

**The item form** (work order, "The item form"), in this order:

- `Item: <handle>` — handles are `IS-B3-FA-nn`, `-SE-nn`, `-WR-nn`, `-GO-nn`.
- **Advances** — the subsystem and the requirement rows of `engine/season/requirements.yaml`.
- **INSTRUCTION** — ordered edits at the single owner: file, symbol, schema, call sites.
- **WHERE** — the edit set (what the file census of U3 §5.1 gains).
- **FALSIFIER and control.**
- **GATE** — an execution artifact and its expected reading; never a document.
- **Hash movers.**
- **Depends on** — batch handles and item handles, each EXISTS-IN-TREE / PROPOSED / MISSING.
- **Lane · batch · cost class · tier · what lands it.**

**Marks.** `[ASSUMPTION: … — basis]` is a reading this lane took and a later lane may reverse. `[UNVERIFIED]` is a claim this lane did not open and does not rely on. `[BLOCKED: reason — owner]` is a missing part not decidable from the repository.

**Words.** `unified/U1_GLOSSARY.md` governs, with A-98: *attribute*, *skill*, *skill score*, *martial skill*, *derived score*; identifiers such as `capability_uses` stay in backticks. "Scenario" is a standalone playable setup of one subsystem (glossary), and in code it is a world: a builder that returns a `World`, never a code path (`11_GO_fidelity_and_campaign_modes.md` §4: "a scenario is a world"). "Stub" is the work order's word; here it means that a neighbour's declared interface is answered either by the neighbour's own registered module, or by a scenario world that holds nothing able to reach it, or by a setting held at a fixed value. It never means a second implementation.

## 1. The standalone-playable test, as this lane applies it

The work order's test has seven parts. Each subsystem section opens with a table of exactly these rows, each marked against the tree today (T) and against the suite's proposals as ordered (P):

| # | part | what counts as met |
|---|---|---|
| S1 | **entry** | one command or harness call that builds the scenario's world and runs it, with choices able to come from outside (a `--pick` or a decider) and from the chooser |
| S2 | **scenario** | a named world or generator seed that exercises this subsystem and no other more than its stub contract requires |
| S3 | **player-facing surface** | the readings the GO proposals name for it (what is asked, what is offered, what came of it, what he has heard) |
| S4 | **stub contract** | for each neighbour, the declared interface (composition row, query, effect) and what answers it |
| S5 | **stop conditions** | the ending kinds (won, lost, drawn), each reachable, none a dead end (A-81), and a held position still moving the world (A-80) |
| S6 | **execution artifact** | a named test or a run with its expected reading, per ending and per stub |
| S7 | **integrated check** | the same subsystem inside the season loop through its registered seam (`04` §A.2, composition rows), with no change of code path |

A part is marked **met** only where a command this lane ran shows it, **carried** where a proposal with a gate carries it (the batch is named), **owed** where an item below carries it, and **blocked** with the reason and owner otherwise.

**GO is not a module.** `unified/U4_TRACEABILITY.md` §3 records it and the tree agrees (no directory under `modules/`, no composition row among the sixteen of `engine/engine_params/composition.json`). For GO the test is read as: can a client that holds no engine state start a game, be offered choices, send one, be shown the result and its reason, reach an ending, save and resume, through the one runner the other subsystems' scenarios use. Its S7 is the port gate (B41).

**WR is three things.** The world's clocks (weather, harvest, wear) are "not a game and not meant to be one" (`audits/09_WR_audit.md` §9.1); threadwork is a module to be registered, with a session a practitioner plays; the era, the strands and the endings are a reading of the log that a seated person lives through. The WR section applies the whole test to threadwork and to the realm as the world's own scenario, and S6 and S7 only to the clocks.

## 2. What the four share: one registry of scenarios, one reading of an ending

Two gaps recur in all four subsystems. The first has an owner in a sibling lane; the second is GO's and is built here.

**Gap 1: a scenario has several names and no owner. Owner: `IS-B2-CORE-01` (lane IS-B2, batch B11).** The suite's proposals name a standalone world by a string in `harness.play_surface … --scenario NAME`, `harness.storybar … --world realm|valley`, `harness.governance_spine play … --world spine|realm`, `harness.headless --world hearing` and `harness/scene.py::FIXTURES`, and three of them write their own season loop. Lane IS-B2's item `IS-B2-CORE-01` (`master/instructions/IS_B2_SC_FI_CORE_CHAR_part2.md` §3.1) answers it: `engine/season/harness/scenarios.py` owns one mapping `SCENARIOS` of frozen `Scenario` rows (`build`, `verbs`, `seat`, `ending`, `role`) and one loop `run(name, seed, seasons, pick=None, host=None)`, which every other entry calls. **This lane builds no second registry.** Its FA, SE and WR items register rows in that one, and `IS-B3-GO-01` (part 2, §6) adds the two row fields this lane's test needs and that item lacks: `kinds` (below) and `unreached` (the roles a scenario's world cannot reach, S4).

**Gap 2: an ending reaches no surface, and has no kind.** FA reads three Queries inside `play`; SE returns `ending: None | "lost" | "held"` from `sheet(w)`; the lean year returns a list from `endings(w, d)`; the realm has `world_q.endings_reached` (`queries/world_q.py:2619`) and the death of the line (`harness/play_surface.py::carry_on`, `:61`). `IS-B2-CORE-01` gives every row one reader, `ending`, which returns a name or `None`. Nothing yet says whether a name is a win, a loss or a draw for the seat, and the player's four readings (`Situation`, `Offer`, `account`, `dossier`) include none that says the run has ended. `IS-B3-GO-01` adds `kinds`, a mapping on the row from each ending name to `won`, `lost` or `drawn`, read from the seated person's side; `IS-B3-GO-02` has the transcript runner stop on an ending and print it.

**What an ending kind is, and is not.** A kind is a label on a scenario's own reading, held in the harness registry. It is not a row of `rosters.yaml: endings`, it adds no `victory:` (the roster's own note records that GD-1 permits exactly one, `rosters.yaml:3443`), and the loop never reads it: `07_SE_valley_scenario.md` §3 states the rule ("a scenario's reading … not a win rule in the engine") and this lane keeps it. `[ASSUMPTION: which of a scenario's endings is labelled won is the scenario author's reading from the seated person's side — basis: the work order asks for "win, lose or draw"; no ruling names a winner of a standalone scenario; reversible by editing one cell of the registry.]`

**The stub contract, in the registry's terms.** For a subsystem played through the loop, lanes IS-B1 and IS-B2 read the stub contract as the row's verb set (`verbs`) and, for a module, as its typed input record. This lane's three loop-played subjects add one measured statement to that: `unreached`, the set of composition roles whose entry count reads 0 on the scenario's world. It is declared from a run, never from intent, and a test holds the declaration to CI-11's reading.

**The reading every integrated check quotes.** `master/CODEBASE_IMPROVEMENT_PROPOSAL_part2.md` item CI-11 (B02) adds an `ENGINES` block to the act-count instrument: composition rows entered, per role. `harness/aperture.py::measure_world(build, seed, seasons)` (`:595`) already takes a builder, so the same block reads a scenario world. Each subsystem's S4 and S7 below name the roles whose counts are quoted before and after.

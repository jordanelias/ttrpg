### E08_felt2019 — Kreminski, Dickinson & Wardrip-Fruin (2019). *Felt: A Simple Story Sifter*
- **Read:** `P (full)` · conference paper · ICIDS 2019 (Springer) · skipped: reference list, acknowledgements · domain: NARR
- **Thesis:** Story sifting (picking storyful event sequences out of a profusion of simulated events) can be implemented simply, by letting authors write human-specified sifting patterns as queries over a database of past events, coupled to a rules-based simulation whose actions use the same patterns. The authors present this as a deliberately naive computational caricature, an argument for the approach rather than a validated best design.
- **Core arguments:**
  1. A sifting pattern is a query: logic variables (slots) plus relations constraining them, returning every combination of bindings that satisfies it, with other events allowed to sit between the matched ones (§1, §3).
  2. Events are stored as database entities with timestamps, a type, a description template and optional effects or cause ids, so the same query machinery runs over everything characters have said and done (§3).
  3. Actions are patterns plus an optional weighting function plus an event constructor; by convention, internal reflection actions produce intent tokens and external actions consume them, which multiplies possible cause/effect routes and makes history-sensitivity visible to the player (§3).
  4. A real query language beat a library of pre-authored accessor functions, because authors' questions cannot be anticipated; the earlier function-library version bottlenecked content on programmer time and was hard to debug (§4.1, §5.1).
  5. Query-backed state also supports debugging (list every currently succeeding pattern, `whyNot` clause isolation), speculative action with rollback, and creativity-support interfaces such as filtering suggestions by variable (§4.2, §5.2).
  6. Sifting is coupled to simulation in practice: every project using Felt's sifting also uses its simulation, because characters reflecting on past events is where the leverage is (§5.3).
- **Argument structure:** Premise: simulations emit many dull events, so something must surface the interesting ones; Ryan's taxonomy names human-specified sequences as one approach. Move: implement that approach in the simplest way (Datalog via DataScript), then show it in three in-development projects (Starfreighter, Cozy Mystery Construction Kit, Diarytown). Evidence is system description, three unfinished case studies, and one small anecdote (four interns authored 85 actions in a week). Weakest link: no evaluation that patterns find stories players find compelling, and no sifting heuristics are implemented; the authors say so (§6).
- **Key terms:**
  - `sifting pattern` — a query seeking ordered sets of events meeting criteria, with other events possibly interspersed.
  - `story support` — surfacing a system-recognised story to the audience (Ryan's term, used here).
  - `intent token` — a fact produced by a reflection action and consumed by an external action, linking interpretation to later behaviour.
  - `sifting heuristic` — a non-specific model of storyfulness used to prefer some sequences over others; not implemented in Felt.
  - `computational caricature` — an oversimplified system that fully realises only the features needed to argue for an approach.
- **Verbatim anchors:**
  - "Felt is a query language-based story sifter coupled with a rules-based simulation engine." (§3)
  - "queries that seek out ordered sets of events matching certain criteria" (§1)
  - "Currently, complicated Felt sifting patterns can be quite long and unwieldy." (§6)
- **Apparatus — tests for a design:**
  - **E08.Q1** *Can a designer ask a new question of the event record (a new sequence shape, with a new constraint) without a programmer writing a new accessor?* Passes if events are queryable data with ordering, actors and types and new patterns are authored as data/queries. Fails if every new interesting thing needs bespoke code. Detects: authoring bottleneck on programmer time.
  - **E08.Q2** *Can a pattern match an ordered pair/set of events with unrelated events interleaved, and also assert that something did not happen in between?* Passes if both interspersal and negation are expressible. Fails if only literal consecutive sequences or only counters/flags can be matched. Detects: brittle literal-sequence recognition.
  - **E08.Q3** *Given a pattern that should match but does not, can the tooling say which clause fails, and can it list every currently-satisfiable pattern with its bindings?* Passes if so. Fails if debugging needs manual stepping through state. Detects: opaque, undebuggable sifting.
  - **E08.Q4** *Does the player see evidence that past events changed later behaviour (a reflection or interpretation step), not only the outcome?* Passes if recognition is surfaced in play. Fails if history-sensitivity is internal and invisible. Detects: the Tale-Spin effect (capability not shown to the audience).
- **Does not license:** That sifting works at scale or finds good stories (no evaluation of sifting output). That query-language authoring is easy for novices (four interns, one week, with a library of examples to copy). That a sifter needs no ranking (the paper defers heuristics). Planning-based generators that emit only interesting events are explicitly outside its definition of sifting (§2). Case studies were in development, not shipped games.
- **Links:** Builds on Ryan's thesis (cited as the origin of story sifting), Ryan et al. 2015, Short's salience-based narrative, Caves of Qud biography generation (Grinblat & Bucklew), Comme il Faut / Versu as internal sifting; Ceptre for action structure.
- **Prior-claim check:**
  - Datalog-style queries over the event log: CONFIRMED (§3: patterns desugar to a subset of Datalog on DataScript; events stored as database entities).
  - `?variable` binding: CONFIRMED (§3, Fig. 1: `?char`, `?eventA`).
  - Attribute constraints: CONFIRMED (§3, Fig. 1: `[?char "trait" "impulsive"]`).
  - Temporal constraints: CONFIRMED (§3: `eventSequence` rule requires one event to precede another, via timestamps).
  - Negative constraints: CONFIRMED (§3: `not-join` tests for nonexistence of an interceding event).
  - Recursive causal rules: CONFIRMED as a capability (§3: rules may be recursive, allowing a `causalRelationship` rule matching indirect causes); CORRECTED in emphasis: it is offered as an example of what rules allow, and is not shown in Fig. 1 or reported as used in a case study.

### E09_winnow2021 — Kreminski, Dickinson & Mateas (2021). *Winnow: A Domain-Specific Language for Incremental Story Sifting*
- **Read:** `P (full)` · conference paper · AIIDE 2021 · skipped: reference list, acknowledgements · domain: NARR
- **Thesis:** Retrospective sifters can only recognise a storyful sequence after it has finished, which blocks foreshadowing, anticipation and live commentary. By requiring patterns to be temporally staged, so each new event only advances, forks or kills tracked partial matches, a sifter can detect microstories while they are still unfolding, and the same patterns can still compile to Felt for retrospective use.
- **Core arguments:**
  1. Existing sifters are retrospective, and anticipation of outcomes is central to how people engage with stories, so a retrospective-only sifter cannot foreshadow or make sense of actions taken with an anticipated outcome in mind (Introduction).
  2. Felt patterns have no explicit temporal structure, so partial variants cannot be derived automatically from them, hand-authoring partials multiplies authoring cost, and re-running variants on every event is expensive (Motivation).
  3. Winnow patterns are a kernel of ordered event clauses plus `unless-event` negations; each is compiled to an acceptor that, per new event, dies, forks-and-accepts, or passes (Winnow: An Incremental Sifting DSL; Incremental Execution).
  4. Incremental matching supports autonomous live commentary (a partial match can be narrated speculatively and later retold as mistaken) and interactive uses (expose a half-matched scheme to the player, accept suggestions, warn of disruption) (Use Cases).
  5. Winnow compiles to a roughly equivalent Felt pattern, with one acknowledged semantic difference: a constraint is checked at its own stage incrementally but at the end of the sequence retrospectively (Retrospective Sifting).
  6. The pool of partial matches grows without bound unless the application prunes it (inactivity timeout, direct advance, death-triggered cleanup); these resemble Ryan's sifting heuristics (Discussion: Pool Management Strategies).
- **Argument structure:** Premise: sifting enables a curationist approach independent of how events are generated, but is retrospective and Felt is low-level. Move: design a DSL whose staged structure gives acceptor semantics, then show it on use cases (a Blaseball-data fatal error pattern, an arson-revenge pattern, the hospitality pattern). Evidence is language description, worked examples, and one benchmark (30 event types, 5 characters, 100 random events, pool of 10 to 1000, average 912 ms per event at 1000, one browser and one laptop). Weakest link: no user study and no test that detected partial matches turn out storyful; likely to be narrated as a fatal error is an assertion by the authors, and the benchmark uses random events, not real simulation output.
- **Key terms:**
  - `incremental sifting` — updating a pool of partial pattern matches as each event arrives, so stories are detected before they finish.
  - `kernel` — the ordered sequence of event clauses in a pattern's body.
  - `unless-event` — a clause that kills a partial match if an event with given properties falls between two kernel events.
  - `acceptor` — the compiled form of a pattern: given a partial match and a new event, it dies, forks-and-accepts, or passes.
  - `prospective narrative intelligence` — reasoning about where a developing sequence may be heading, as against purely retrospective interpretation.
- **Verbatim anchors:**
  - "Dies if this event matches an active unless-event constraint on this event sequence." (Incremental Execution)
  - "As a result, Winnow sifting patterns are by default written in a causality-agnostic way." (Discussion: Modeling Causality)
  - "Winnow makes no attempt to remove partial pattern matches from the pool, except when" (Discussion: Pool Management Strategies)
- **Apparatus — tests for a design:**
  - **E09.Q1** *Can the system recognise a developing sequence (not just a finished one) and use it while the sequence is still open, for foreshadowing, warning or suggestion?* Passes if a partial-match state exists and something consumes it. Fails if narrativisation waits for completion. Detects: retrospective-only story recognition.
  - **E09.Q2** *Is there a stated policy that bounds the set of in-progress candidate stories (timeout, death/invalidation cleanup, duplicate collapse)?* Passes if candidates can leave the pool and duplicates differing only in event specifics are merged or suppressed. Fails if candidates accumulate indefinitely or the player sees near-duplicate story threads. Detects: unbounded candidate growth.
  - **E09.Q3** *For a pattern constraint on a changing attribute (a trait, loyalty, office), does the pattern say at which event it must hold?* Passes if the stage is explicit. Fails if the check happens only on end-state, so a later change silently invalidates or validates the match. Detects: temporal-scope ambiguity.
  - **E09.Q4** *Can the sifter run over the event output without modifying the generating process?* Passes if the sifter consumes a plain event log. Fails if recognition requires hooks inside every simulation rule. Detects: coupling that prevents adding narrative intelligence to an existing engine.
- **Does not license:** That incremental detection predicts the story's outcome (a partial match can be wrong; the paper's own example imagines commentary later retold as mistaken). That 912 ms per event is acceptable for any real game (benchmark is synthetic, small-cast, pool-size-driven). That causal tracking is unnecessary: Winnow is causality-agnostic by default so it can read engines lacking causal bookkeeping; the authors say bookkeeping greatly aids curation. Evidence is a language paper with worked examples, not a play study.
- **Links:** Builds on Felt (E08), Ryan's thesis (sifting heuristics, causal bookkeeping), Synthesifter, Caves of Qud (retrospective-only), Marie-Laure Ryan on baseball commentary; mentions The Sims 2 story trees as the closest prior prospective approach.
- **Prior-claim check:**
  - Winnow detects storyful sequences incrementally while they play out: CONFIRMED (Abstract; Incremental Execution).
  - Winnow translates to Felt patterns: CONFIRMED with qualification (Retrospective Sifting: compiles to a roughly equivalent Felt pattern; the stage-specific constraint timing differs, and the authors present compilation as the retrospective mode, not the main contribution).

### E10_stu2022 — Kreminski, Dickinson, Wardrip-Fruin & Mateas (2022). *Select the Unexpected: A Statistical Heuristic for Story Sifting*
- **Read:** `P (full)` · conference paper · Springer LNCS format; the extracted text does not name the venue (ICIDS 2022 is the expected venue, but it is [reader's inference]; references run to mid-2022) · skipped: reference list, acknowledgements · domain: NARR
- **Thesis:** Once a sifter has many patterns, each yielding hundreds or thousands of matches, it needs a way to choose which matches to surface. Preferring matches whose properties are statistically rare among other matches of the same pattern surfaces more interesting microstories than random choice, and lets patterns be generic.
- **Core arguments:**
  1. Pattern-based sifting creates a second problem, selection among many matches, and sifting heuristics (generic encodings of tellability) were proposed by Ryan but not seriously implemented (§1, §2.2).
  2. The StU heuristic builds a property signature for each match (event types, tags, character traits, dyadic relationships, same-character coincidences), measures how often each property occurs across all matches of that pattern, averages those frequencies per match, and surfaces the lowest averages (§4, Algorithm 1).
  3. A blind pairwise comparison against random selection found raters picked the heuristic's match in 38 of 45 judgments (84.44%), with per-pattern agreement from 77.78% to 100% (§5.1, Table 1).
  4. The surfaced unusual matches fall into recognisable kinds: globally rare event types, pattern-rare event types, characters more related than necessary, contradictory relationships, characters acting against type (§5.2).
  5. In a two-layer design, patterns should capture narrative structure without regard to tellability and leave tellability to the heuristic; generic patterns then give the heuristic more matches to choose among (§6.1).
  6. Per-property scores give built-in explanation of why a match was chosen, which could mitigate the Tale-Spin effect (§6.1).
- **Argument structure:** Premise: a story is tellable partly because it deviates from expectation, so unexpectedness operationalised as statistical rarity within a pattern's match population is a usable proxy. Moves: define the heuristic, test it on a toy simulation, add cherry-picked successes, and argue it would rediscover Ryan's arson-revenge story from a generic revenge pattern. Evidence: one simulation run (1000 events, 24 action types, 20 characters, actions chosen at random weighted by traits/relationships), five patterns, 15 pairs, three raters. Weakest link: the 45 judgments come from only 15 pairs and three raters (the authors call the result tentative), two patterns had only 13 and 12 matches, the examples are admitted cherry-picks, and the arson-revenge result is argued (would stand out), not run.
- **Key terms:**
  - `sifting heuristic` — a higher-level, pattern-independent model of what makes a match worth surfacing (Ryan's term).
  - `StU` — Select the Unexpected: rank matches by lowest average property likelihood.
  - `property signature` — a set of simple true statements about a match, e.g. `eventHasType_e3_set-fire`, `sameChar_c1_c3`.
  - `likelihood score` — the match's average of per-property frequencies among all matches of the same pattern; lower means more surprising.
  - `extrapolative narrativization` — a reader inventing motives consistent with events but beyond what the simulation models.
- **Verbatim anchors:**
  - "Matches with lower likelihood scores are more surprising and therefore preferable to surface." (§4, Algorithm 1)
  - "patterns should be written to capture event sequences that have narrative structure" (§6.1)
  - "it remains possible that the raters were all outliers in this regard" (§6.2)
- **Apparatus — tests for a design:**
  - **E10.Q1** *When many instances of a story pattern exist, what decides which are surfaced, and is that rule better than random in a blind comparison?* Passes if a stated selection rule exists and has been compared with random on blind pairs. Fails if surfacing is first-found, most recent or random, or the rule is asserted but never tested. Detects: unranked sifting output and unvalidated interestingness.
  - **E10.Q2** *Is unusual measured against the population of matches of the same pattern (context), not against global event frequency alone?* Passes if rarity is computed per pattern or context. Fails if only global rarity is used, so a common event in a rare context is missed. Detects: context-blind novelty.
  - **E10.Q3** *Can the system say which property made a surfaced story stand out?* Passes if a per-property reason can be shown to the player or log reader. Fails if selection is an opaque score. Detects: Tale-Spin effect (opaque output hides the system's work).
  - **E10.Q4** *Does the ranker discount rarity that is expected from the world's own rules (a rare villain who always does the rare villainous act)?* Passes if correlated properties are not double-counted. Fails if the stories most surfaced are those whose rarity is caused by one underlying fact. Detects: correlated-unlikelihood false positives (the paper's own stated limitation).
- **Does not license:** That 84% agreement generalises: three raters, one run, a text-only presentation the authors call a worst case, and a random-event toy simulation in which unusual by construction means rare action draws. That statistical rarity equals narrative quality (it is one operationalisation of surprise; the authors say relatively naive). That it was validated on Ryan's arson-revenge case (argued only). That it needs no authored patterns: it ranks matches that patterns find, so rare unpatterned stories are invisible to it.
- **Links:** Builds on Ryan's thesis (sifting heuristics, arson-revenge), Felt (E08), Winnow (E09), Synthesifter's property generation, Baroni on tellability, Indexter; cites Bad News interaction analysis as an alternative source of heuristics.
- **Prior-claim check:**
  - Ranks sifting-pattern matches by statistical improbability: CONFIRMED with exact form (§4, Algorithm 1): score = average, over a match's properties, of each property's frequency among all matches of the same pattern; lowest score preferred. Evaluation (§5): one simulation run, five patterns, 15 pairs (a top-3 heuristic match vs a random match per pattern), three raters, 38/45 = 84.44% agreement; plus cherry-picked examples and a hypothetical arson-revenge generalisation. Authors confirmed as Kreminski, Dickinson, Wardrip-Fruin, Mateas.

### E15_qud2017 — Grinblat & Bucklew (2017). *Subverting Historical Cause & Effect: Generation of Mythic Biographies in Caves of Qud*
- **Read:** `P (full)` · conference paper (system description with qualitative evaluation) · FDG 2017 · skipped: copyright block, reference list; two-column extraction is interleaved at §4.1-4.2 but readable · domain: PCG
- **Thesis:** To produce history as an in-world artefact (an account the player encounters), a game need not simulate historical causation. It can pick events at random, apply them to an entity's state, and then rationalise each one afterwards from that state, letting shared state and player apophenia supply coherence.
- **Core arguments:**
  1. The design goal is generated historical accounts, not historical process, so no simulation of underlying logic is attempted; this contrasts with Dwarf Fortress, which must stay agnostic about what is past because play can start mid-history (§1, §3).
  2. Each sultan is an entity with a few core properties and a domain; life events are chosen at random, resolve outcomes partly from state and partly from random branching, and then update state; about thirteen events follow initialisation and a death event closes the life if needed (§4.2).
  3. Causality is reversed: events are random, but each event's gospel text pulls a cause from the sultan's current state, or alters state to create a missing cause (the example is adding frogs as allies) (§4.3).
  4. Coherence comes from shared state acting as glue, above all the domain symbol that nearly every grammar pattern contains, so micro-narratives (the cats episode) arise without being planned (§4.4).
  5. A Tracery-like replacement grammar stored as nested JSON, queried through a custom query language, maps state to text in the game's voice; histories also instantiate sites and items in the world (§4.5, §4.6).
  6. Evaluation is qualitative: six months with players, gospels in 14 of the 150 top screenshots, no explicit coherence complaints, and the authors' own honing through generating many sultans (§5).
- **Argument structure:** Premise: players meet history as an artefact filtered through the present, so accounts can be evocative and need not be causally faithful. Moves: choose a small closed set of rulers, give each a state vector and a domain, make events state-parameterised random draws with ex post facto rationalisation, then show one full generated biography (Table 1). Evidence: a system description, one worked example, developer assessment, a screenshot count and absence of complaints. Weakest link: coherence is judged largely by the authors, the journal that juxtaposes gospels was added only recently, permadeath means few players see several gospels from one sultan, and the authors concede the player-complaint evidence is of limited weight.
- **Key terms:**
  - `gospel` — a single-event text snippet; the basic discrete unit of generated history.
  - `domain` — an archetypal cultural unit (ice, stars, might...) assigned to a sultan, appearing in nearly every pattern as a narrative thread.
  - `ex post facto rationalisation` — choosing an event first and then deriving or inventing its cause from state.
  - `apophenia` — the player's tendency to perceive patterns, deliberately relied upon for coherence.
  - `historical entity` — a place, item or sultan represented as a data structure that events modify.
- **Verbatim anchors:**
  - "Our system first decides that a particular historical event will occur" (§1)
  - "Events themselves are chosen at random, though their gospels often profess causes." (§4.3)
  - "using existing state to rationalize narrative events after the fact" (§6)
- **Apparatus — tests for a design:**
  - **E15.Q1** *Do successive events read and write a small shared set of properties on the same entity, so a later event can cite an earlier one's residue?* Passes if properties created by one event are demonstrably reused by later events. Fails if each event is generated independently. Detects: disjointed event sequences with nothing for a reader to connect.
  - **E15.Q2** *Where a chronicle line states a cause, is that cause a recorded causal fact in the engine, a state-derived rationalisation, or an invented one, and does the design say which?* Passes if the category is declared and invented causes are written back to state. Fails if the line asserts causation the engine neither computed nor stored, with no flag. Detects: unlabelled fabricated causality.
  - **E15.Q3** *Does each generated actor carry a thematic seed that most text patterns draw on, giving random events a recognisable character?* Passes if a seed symbol appears across most event texts. Fails if events read as interchangeable. Detects: voiceless randomness.
  - **E15.Q4** *Is the coherence claim tested on players who see multiple fragments together, and is the sample (how many ever do) reported?* Passes if sample size and exposure conditions are reported. Fails if coherence is judged by the author reading output or by absence of complaints. Detects: author-satisfaction mistaken for player reception.
- **Does not license:** That random-then-rationalise suits a game whose histories must be consistent with the player's own actions (here the histories are fixed pre-play, tertiary to the critical path, and the paper contrasts itself with simulating history). That coherence was established by player study (evidence is self-assessment, screenshots, and silence). That it generalises beyond five rulers of one authored voice with a 40,000-word text corpus behind it. It is a generation method for a subordinate system, not an emergent-narrative architecture.
- **Links:** Cited by Felt (E08) as using sifting patterns to retroactively justify random actions [that reading is Felt's, not this paper's own terminology]; builds on Tracery, Schrödinger's Gun (Robertson & Young), contrasts with Dwarf Fortress, Bad News, Ultima Ratio Regum; Opera Omnia on history's rhetorical function.
- **Prior-claim check:**
  - State machine + Tracery-like replacement grammar over a ~40k-word authored corpus: CORRECTED. State machine and replacement grammar are named (Abstract); Tracery-like is §4.2. The over 40,000 words figure is the size of the game's whole text corpus that establishes its voice (§5); the grammar is a static nested JSON of curated fragments codifying that diction, not a grammar run over the corpus.
  - Generate events first, rationalise afterwards: CONFIRMED (Abstract, §1, §4.3).
  - Dual register, clean grammar for canonical texts vs order-2 Markov for deliberately corrupted texts: NOT-IN-SOURCE (no Markov or corrupted-text register anywhere in the paper; searched).
  - Sultan history = origin → 8 core events from a pool of 17 → ascension → death, state chained: CORRECTED. Structure is initialisation → one random event plus about twelve more (about thirteen) → generic death event if still alive (§4.2); the event pool is nineteen, domains ten (§6); ascension is an outcome inside a challenge-sultan event (§4.5), not a stage; no 8 and 17 appear nowhere. State chaining CONFIRMED (§4.2: each event parameterised by the state at its start and transitions the sultan to a new state).

### E17_adams_gameaipro — Adams (2015). *Simulation Principles from Dwarf Fortress* (Game AI Pro 2, ch. 41)
- **Read:** `P (full)` · book chapter (practitioner chapter, about 3 pages) · Game AI Pro 2, Analytics, Content Generation, and Experience Management section · skipped: reference list · domain: PCG
- **Thesis:** A simulation-based generator stays robust and tunable if the developer builds it iteratively, decomposes it into basic elements and their interactions, keeps variables to what has meaningful impact, and borrows structure from a real-world analog. The chapter's examples are all about generating the physical world map, not stories or characters.
- **Core arguments:**
  1. Do not overplan the model: results of simulation-based generation cannot always be predicted, so get something running early and iterate, and enjoy what emerges (§41.2).
  2. Break the system down into basic elements and interactions; generating separate fields (temperature, rainfall, elevation, drainage) and letting their interplay determine the biome gave better, more internally consistent results than spawning biomes directly (§41.3).
  3. Do not overcomplicate: operate at the level of what the player sees or one layer below, and avoid variables that do not meaningfully affect the game, since they hinder tuning (§41.4).
  4. Base the model on real-world analogs, which let you correct defects from known fundamentals (rain shadows and drainage improved the maps) (§41.5).
  5. Combined, the principles give results that are varied, surprising and responsive to adjustment, and avoid black-box simulation (§41.6).
- **Argument structure:** Premise: simulation-driven content is hard to predict and easy to over-build. Moves: four rules of thumb, each backed by one Dwarf Fortress terrain-generation anecdote. Evidence is the author's experience as the developer, with no measurement or comparison. Weakest link: every example comes from physical-world generation, where a real-world analog exists; the chapter does not show the principles transfer to social, political or narrative simulation, where no such analog can correct defects.
- **Key terms:**
  - `model` — the set of simulated fields, objects and interactions the generator runs.
  - `real-world analog` — a real phenomenon whose known behaviour guides and debugs the model.
  - `black box simulation` — a simulation whose behaviour the developer cannot understand or adjust.
  - `the level of what the player sees or one layer below` — the depth of modelling the author recommends.
- **Verbatim anchors:**
  - "Rather than overplanning the model, build it up through iteration." (§41.2)
  - "Operate at the level of what the player sees or one layer below." (§41.4)
  - "you can avoid black box simulations and ultimately stay in control of your game." (§41.6)
- **Apparatus — tests for a design:**
  - **E17.Q1** *For each simulated variable, can the design name the player-visible effect it has or the one-layer-below quantity that does?* Passes if every variable traces to a visible consequence. Fails if variables exist whose changes nobody could observe in play. Detects: worthless-noise complexity.
  - **E17.Q2** *Is each important outcome derived from the interplay of separately modelled components, rather than assigned directly?* Passes if the outcome is computed from two or more independent inputs. Fails if the outcome is specified top-down and the components are decoration. Detects: faked emergence.
  - **E17.Q3** *Does each subsystem have a stated real-world referent, and has any defect been corrected by consulting it?* Passes if a referent is named and a correction from it is on record. Fails if no referent exists and defects can only be patched ad hoc. Detects: unanchored model.
  - **E17.Q4** *Can a designer adjust a parameter and see the response in a short loop?* Passes if the model was run early and is run per change. Fails if behaviour can be seen only in a late integrated build. Detects: overplanned, un-iterated model.
- **Does not license:** Any claim about narrative, character or story emergence: the chapter says nothing about stories, sifting, or the player's role. It does not state a method of writing intended stories first, nor describe players as agents of an official will (both searched, absent). Four rules from one developer's anecdote; real-world analogs help terrain and may mislead for social or political systems, which the chapter does not address.
- **Links:** Cites only the Dwarf Fortress site and the PCG wiki; no corpus item. Felt (E08) cites a different Adams text (a 2019 chapter on emergent narrative in Dwarf Fortress), not this chapter.
- **Prior-claim check:**
  - Four principles: don't overplan the model; break down and understand the system; don't overcomplicate; base the model on real-world analogs (§41.2-41.5).
  - Write the stories you want the game to produce, then build the engine: NOT-IN-SOURCE (the chapter advises the reverse: get something running and iterate, then enjoy what emerges).
  - The player as the official will with the dwarves as actors in their own stories: NOT-IN-SOURCE.

### E12bcd_short_on_ryan — Short (2019) on Ryan (2018), *Curating Simulated Storyworlds*
- **Read:** `S` (Emily Short's three-part blog reading of James Ryan's PhD thesis; every argument below is Ryan AS REPORTED BY SHORT unless marked Short) · blog posts (three: ch. 1-3, ch. 4-5, ch. 6 onward) · Emily Short's Interactive Storytelling · skipped: site chrome; comment threads read selectively (one commenter's idea and one reply by Short are cited) (dates are not in the extracted text; the brief gives May 2019) · domain: MIX. Files: E12b, E12c, E12d.
- **Thesis:** As Short reports it, Ryan argues that emergent narrative works like nonfiction because its events actually happened in a simulation, that raw simulation output almost never has story structure, and that the remedy is curation (a human or second system extracting and presenting the good stories) rather than steering the simulation with a drama manager.
